# Dev Workflow — AI 感知驱动的渐进式开发方法论

> **核心理念**: 用户只需聊天。AI 负责感知阶段、创建文档、追踪关联、发现冲突。
> 适用于全新项目和既有项目改造。

## 1. 阶段感知

AI 根据对话内容自动判断当前阶段，**不要求用户显式切换**：

| 信号 | 判定阶段 | AI 动作 |
|------|---------|--------|
| 用户描述想做的东西、场景、痛点 | **头脑风暴** | 创建 BRIEF，追问澄清（最多 5 个关键问题），更新 DESIGN-BOARD |
| 用户问"怎么做""选哪个"或讨论技术方案 | **澄清** | 建议创建 CONSTITUTION/ARCHITECTURE，提炼决策点 |
| 需要做技术选择、有明确利弊需要决定 | **固化** | 起草 ADR，列出利弊和影响范围，请用户确认 |
| 用户说"开干""做吧"或具体实现细节已定 | **施工** | 创建 SPEC + PHASE，按规格施工 |
| 施工完成或用户要求审查 | **验证** | 审查是否匹配 SPEC，更新 PHASE 状态 |
| 新想法与旧决策冲突，或多功能重复 | **收敛** | 扫描关联，标记影响范围，提出合并建议 |

### 1.1 多信号优先级

当用户一句话触发多个阶段时，按以下优先级处理：

1. **冲突 > 收敛 > 澄清 > 施工 > 头脑风暴**

但如果用户明确说"先做着"，则施工优先。

### 1.2 追问上限

每次头脑风暴最多追问 **5 个关键问题**。追问完后给用户出口：
- "这些够我开始了，要继续深入某个方向吗？还是先记录？"
- 用户说"先记下来"→ 结束追问，BRIEF 保持模糊即可
- 用户说"继续讨论 X"→ 深入 X，重新计数 5 个问题

### 1.3 多想法处理

一次对话抛出多个独立想法 → **各建一个 BRIEF**，在 DESIGN-BOARD 中标注关联。

一个想法衍生多个子方向 → **一个 BRIEF + 子节**，子方向在澄清阶段再决定是否拆分。

## 2. 命名与编号规范

所有项目文档使用统一命名规则：

```
BRIEF-001-clustering.md      # NNN-slug 格式，slug 用英文小写连字符
ADR-001-embedding.md
SPEC-001-fts5-index.md
PHASE-001-index-worker.md
REVIEW-2026-05-15.md         # 日期格式 YYYY-MM-DD
```

编号自动递增：AI 扫描 `docs/briefs/` 目录找最大编号 +1。

ADR/DDR 兼容：如果项目已有 `DDR-*.md` 或 `docs/adr/` 中已有文件，沿用现有编号体系，不重排。

## 3. 流转规则

1. **用户一句话可能触发多阶段**——按优先级处理（见 §1.1）
2. **不要跳过阶段**——没澄清就直接施工是危险的（除非用户明确说"先做着"）
3. **但不要阻塞用户**——如果用户说"先做着"，可以先施工再补文档
4. **渐进落笔**——想法先在 DESIGN-BOARD，澄清后转 ADR，施工时转 SPEC
5. **BRIEF 不是墓碑**——超过 30 天未推进的 BRIEF，AI 在会话开始时间用户"要不要继续讨论或关闭"

## 4. 冲突管理

### 4.1 冲突检测

当新输入与已有 ADR/SPEC 冲突时：

1. **静默扫描**——不打断用户，先对比 DESIGN-BOARD + 所有 ADR
2. **ADR 筛选规则**——主 AI 按以下条件筛选相关 ADR：
   - 关键词匹配：新输入中的术语与 ADR 标题/背景的关键词重叠
   - 模块匹配：新输入涉及的模块名与 ADR 影响范围中的模块重叠
   - 明确引用：用户说"之前的 ADR-003"或"那个聚类的决策"
3. **调 conflict-resolver agent**——传入筛选后的 ADR + 新输入

### 4.2 冲突分类

- **轻微冲突**（参数调整，不改变方向）→ 主 AI 直接更新 ADR 理由字段，告知用户
- **根本冲突**（方向矛盾，推翻已有决策）→ conflict-resolver agent 分析影响范围，呈现给用户

### 4.3 施工中遇冲突

当冲突涉及的 SPEC 有活跃 PHASE（状态="施工中"）时：

1. PAUSE 该 PHASE —— 状态改为"暂停: 等待冲突解决"，记录暂停原因
2. 冲突解决后：
   - 推翻旧决策 → PHASE 标记"废弃"，重建新 SPEC + PHASE
   - 并存 → PHASE 继续，缩小范围
   - 撤回 → PHASE 恢复"施工中"

### 4.4 用户决策选项

呈现给用户三个选项：
- **推翻旧决策** → ADR 标记 `superseded`（注明被哪个新 ADR 替代），新建 ADR，受影响 SPEC 重做
- **并存** → 缩小旧 ADR 范围 + 新建 ADR，保留现有代码
- **撤回** → 保留旧 ADR，新想法暂存 BRIEF

## 5. 架构收敛

AI 定期主动扫描，不在用户任务清单里：

| 触发条件 | 动作 |
|---------|------|
| 每新增 3 个 ADR | 扫描关联，提出可合并/抽象的建议 |
| 每新增 5 个 SPEC | 启动 converge-scanner agent 审查 |
| 冲突解决后 | 扫描受影响模块，更新 DESIGN-BOARD 关联 |

### 5.1 收敛扫描的代码摘要

主 AI 为 converge-scanner agent 准备代码摘要时：
- 读 ARCHITECTURE.md 的模块列表 → 每个模块的入口文件（`src/xxx.py` 或 `scripts/_lib/xxx.py` 的首 50 行）
- 读所有 SPEC 的"关联模块"字段 → 相关文件的函数签名（`def xxx(...)` 的行）
- 不传完整代码，只传摘要（每个模块 < 200 tokens）

### 5.2 审查结果通知

`REVIEW-YYYY-MM-DD.md` 写入后：
1. 立即告知用户："架构收敛扫描发现 N 个建议，要现在看吗？"
2. 下次会话开始时，如果上次有未读 REVIEW，提醒用户

## 6. 跨会话上下文恢复

每次新会话开始时，AI 执行以下启动序列：

```
1. 读 DESIGN-BOARD.md → 了解项目整体状态
2. 读所有 PHASE-*.md → 找到活跃/暂停的 Phase
3. 如果有活跃 Phase → 读关联 SPEC → 继续施工
4. 如果有暂停 Phase → 告知用户"上次 X 暂停了，要继续吗？"
5. 如果有未读 REVIEW → 提醒用户
6. 如果有超过 30 天未推进的 BRIEF → 问"要继续讨论吗？"
```

## 7. 既有项目改造

### 7.1 反向工程（代码 → DESIGN-BOARD）

对于没有 `docs/` 结构的既有项目，执行以下步骤：

```
Step 1: 扫描项目根目录 → 识别项目类型（插件/Skill/Web/CLI）
Step 2: 读取 CLAUDE.md（如有）、README.md → 提取核心原则
Step 3: 读取主入口文件 → 提取模块列表
Step 4: 读取 config / settings 文件 → 提取技术栈
Step 5: 生成初始 DESIGN-BOARD.md、CONSTITUTION.md、ARCHITECTURE.md
Step 6: 向用户确认："我从代码中推断出以下结构，准确吗？"
Step 7: 用户修正 → 文档定稿
```

### 7.2 单体文档迁移

如果项目有一个大型设计文档（如 `paper-factory-design.md` 3 万字）：

```
Step 1: 解构——AI 读全文 → 提取为：
  - CONSTITUTION.md（技术栈、核心原则）
  - ARCHITECTURE.md（模块边界、数据流）
  - ADR-*.md（每个 DDR 一个文件）
Step 2: 保留原文档——不移除、不删除，新建 `docs/` 目录作为并行结构
Step 3: 渐进迁移——每次施工时，将涉及的部分从旧文档迁移到新结构
Step 4: 原文档在顶部添加提示："已迁移至 docs/ 结构化文档，本文档保留为历史参考"
```

## 8. 文件体系

在用户项目中创建以下结构：

```
docs/
├── DESIGN-BOARD.md           # 设计版图（持续更新）
├── CONSTITUTION.md            # 项目宪章（几乎不变，含 NFR）
├── ARCHITECTURE.md            # 系统架构（偶尔变）
├── briefs/                    # 头脑风暴产出
│   └── BRIEF-NNN-slug.md
├── adr/                       # 决策记录（含依赖链）
│   └── ADR-NNN-slug.md
├── specs/                     # 施工规格
│   └── SPEC-NNN-slug.md
├── phases/                    # 进度追踪 + 并行检测
│   └── PHASE-NNN-slug.md
├── milestones/                # 里程碑（可选）
│   └── MILESTONE-NNN-vX.Y.Z.md
└── reviews/                   # 收敛审查
    └── REVIEW-YYYY-MM-DD.md
```

## 9. 激活机制

此 Skill 通过 `description` 字段中的关键词触发。当用户表达以下意图时，AI 根据 description 匹配判断应调用此 Skill：

- 描述一个新项目想法（"我想做..."、"我需要一个..."）
- 讨论技术方案或架构（"怎么设计..."、"用什么技术..."）
- 管理需求（"帮我规划..."、"整理一下需求"）
- 既有项目改造（"这个项目要加新功能..."、"重构..."）

用户也可显式触发：`/dev-workflow` 或 "启动开发方法论"。

> AI 注意：此 Skill 通过 available-skills 列表注入。如检测到上述意图信号且 Skill 未加载，主动调用 Skill 工具加载之。

## 10. 质量门禁

每个阶段进入下一阶段前必须满足的条件：

| 阶段转换 | 门禁条件 |
|---------|---------|
| 头脑风暴 → 澄清 | BRIEF 中有 ≥1 个核心问题 + ≥1 个初步设想方向 |
| 澄清 → 固化 | 有 ≥1 个明确的"二选一/多选一"决策点，且用户已看过选项 |
| 固化 → 施工 | ADR 状态="已采纳"，SPEC 中施工清单清晰（每项可独立验证） |
| 施工 → 验证 | PHASE 状态="已完成"，所有验收标准勾选 |
| 任意 → 收敛 | 触发条件满足（§5），无需前置门禁 |

**门禁不是阻塞**：如果用户说"先做着"，可以跳过门禁，但在 DESIGN-BOARD 中标记"跳过了门禁"以便后续回头补。

## 11. 用户拒绝处理

当 AI 的建议被用户拒绝时：

1. **不要反复提议同一个方案**——记录到 DESIGN-BOARD 的关联发现中，标记"已讨论，用户拒绝"
2. **提供替代方案**——"好的，那我们换一个方向。A 不行的话，B 或 C 呢？"
3. **如果三个方案都被拒**——"看来这个决策点需要更多信息。我们先放一放，等你了解更多后再定？"
4. **BRIEF/ADR 被拒不删除**——保持原样，状态标记为"已拒绝: {{日期}}"，保留历史可追溯

## 12. 范围管理

### BRIEF 拆分

当 BRIEF 覆盖 ≥3 个独立功能方向时，拆分为多个 BRIEF：
- 原始 BRIEF 保留，增加"已拆分"注释指向前 BRIEF 编号
- 新 BRIEF 各覆盖一个方向

### SPEC 拆分

当施工清单 > 10 项时，拆分为多个 PHASE：
- SPEC 不变，每 PHASE 覆盖 3-5 项
- PHASE 按依赖排序

### 范围蔓延

当 BRIEF 在澄清过程中不断膨胀，AI 应主动提醒：
- "这个想法从最初 X 扩展到了 Y 和 Z。要不要先把 X 做完，Y 和 Z 作为独立的 BRIEF？"

## 13. Git 集成

| 时机 | 操作 |
|------|------|
| 新建/修改任何 `docs/` 文件 | 建议 `git add docs/ && git commit -m "docs: ..."` |
| ADR 状态变更 | 单独 commit：`git commit -m "adr: ADR-003 已采纳"` |
| PHASE 完成 | commit 关联代码：`git commit -m "feat: xxx (PHASE-001 完成)"` |
| REVIEW 生成 | commit：`git commit -m "review: 架构收敛扫描 YYYY-MM-DD"` |

不要在施工代码的 commit 中混杂文档变更。文档变更和代码变更分开 commit。

## 14. 使用示例

### 新项目对话

```
用户: "我想做个命令行工具，能批量下载论文 PDF 然后提取文字"

AI 内心: [头脑风暴] → 创建 BRIEF-001-pdf-downloader.md
AI: "明白了。先确认几个关键点：
     1. 论文来源是什么？PubMed？arXiv？还是特定的期刊网站？
     2. 提取文字后做什么？全文搜索？还是结构化存储？
     3. 你是自己用还是给别人用？"
     [追问不超过 5 个问题]

用户: "PubMed，自己用，主要是全文搜索"

AI 内心: [澄清] → 更新 DESIGN-BOARD
AI: "了解了。技术方案有两个方向：
     A) Python CLI + SQLite FTS5 — 简单、单机、秒级搜索
     B) Elasticsearch — 功能更强但需要额外部署
     你倾向哪个？"

用户: "A，简单就好"

AI 内心: [固化] → 创建 ADR-001-sqlite-fts5.md
AI: "ADR-001 已记录：用 SQLite FTS5 做全文搜索。
     接下来要开始施工吗？还是先把其他功能也讨论完？"
```

### 既有项目对话

```
用户: "factory 项目要加用户认证功能"

AI 内心: [检测到既有项目] → 读 DESIGN-BOARD + 已有 ADR
AI: "好的。当前项目状态：14 个 ADR，13 个已施工。
     用户认证是全新方向——我先创建 BRIEF-015-auth.md。
     另外，认证可能会影响已有的 worker 调用模式，
     需要标记为收敛扫描的待检查项。"
```

## 15. 不适用场景

此 Skill **不应该**用于以下情况：

- 简单 bug 修复（改一行代码）
- 文档错字修正
- 已有明确指令的单步操作（"帮我把这个文件重命名为 X"）
- 纯研究/探索性对话（"帮我查一下 XXX 是什么意思"）

> 判断标准：如果任务需要 ≥2 个步骤且涉及设计选择 → 使用此 Skill。否则直接做，不建文档。

## 16. 模板使用说明

### 16.1 查找模板

模板位于此 Skill 的 `templates/` 目录中。AI 查找方式：

1. 从当前加载的 SKILL.md 路径推导：`{SKILL.md 所在目录}/templates/{TEMPLATE}.md`
2. 例如 SKILL.md 在 `/path/to/dev-workflow/SKILL.md` → 模板在 `/path/to/dev-workflow/templates/ADR.md`

> 模板路径不是硬编码的——始终从 SKILL.md 的实际位置推导。

### 16.2 使用模板

1. **复制模板内容** → 替换 `{{placeholder}}` 为实际值
2. **不要留下 `{{placeholder}}`** — 如果某项不适用，写 `N/A` 而非保留占位符
3. **文件名按 §2 命名规范**：`{TYPE}-{NNN}-{slug}.md`
4. **日期格式**：`YYYY-MM-DD`
5. **模板是起点** — 可根据项目需要增加字段，但不要删除核心字段

## 17. 错误恢复

文件创建操作可能失败（权限、磁盘满、路径不存在等）。AI 处理规则：

1. **创建父目录** — 写入 `docs/briefs/BRIEF-001.md` 前，确保 `docs/briefs/` 目录存在
2. **原子写入** — 先写临时文件，确认成功后再 rename 到目标路径
3. **关联更新滞后** — 如果 DESIGN-BOARD 更新失败，ADRs/SPECs 已写入不受影响。下次会话检测到孤立文件时自动补注册
4. **不静默失败** — 任何 IO 错误立即告知用户，附文件名和错误原因

## 18. docs/ 目录位置

### 新项目

`docs/` 放在项目根目录。如果项目是 Git 仓库，`docs/` 在仓库根下。

### 既有插件项目（如 paper-factory）

插件有自己的目录约定（`.claude-plugin/`、`skills/`、`src/`）。`docs/` 仍放在插件根目录，与 `.claude-plugin/` 同级。这是 Claude Code 插件的标准做法。

### 既有非插件项目

检测项目根 → `docs/` 放在项目根。项目根识别：有 `.git/`、`package.json`、`CLAUDE.md` 或 `README.md` 的目录。

## 19. PHASE 状态机

```
待开始 ──→ 施工中 ──→ 已完成
              │
              ├──→ 暂停（用户中断 或 冲突等待解决）
              │       │
              │       ├──→ 施工中（冲突已解决，恢复）
              │       └──→ 废弃（冲突导致方向推翻）
              │
              └──→ 废弃（用户主动放弃 或 ADR 被 superseded）
```

状态变更触发条件：

| 转换 | 触发条件 |
|------|---------|
| 待开始 → 施工中 | AI 开始执行 SPEC 施工清单第一项 |
| 施工中 → 已完成 | 所有验收标准勾选，AI 审查通过 |
| 施工中 → 暂停 | 用户说"先停一下" 或 冲突涉及此 PHASE（§4.3） |
| 暂停 → 施工中 | 用户说"继续" 或 冲突解决且用户选择"并存" |
| 暂停 → 废弃 | 冲突解决且用户选择"推翻旧决策" |
| 施工中 → 废弃 | 用户主动放弃此功能 |
| 任何 → 废弃 | 关联 ADR 状态变为 superseded |

## 20. 看板视图

用户说"看板"或"现在什么状态"或"show board"时，AI 读取 DESIGN-BOARD.md 并以结构化格式呈现：

```
=== 项目看板: paper-factory ===

📋 已识别 (3):
  P1 BRIEF-015 用户认证
  P2 BRIEF-016 数据导出
  P3 BRIEF-017 批量操作

🔍 澄清中 (1):
  BRIEF-015: 用 JWT 还是 Session？

✅ 已决策 (14 ADR, 全部已采纳)

🏗️ 施工中: 无

🔔 收敛建议: REVIEW-2026-05-15 (未读)

下一步建议: 继续讨论 BRIEF-015 的技术方案
```

不需要读所有文件——只读 DESIGN-BOARD.md + 活跃 PHASE 文件 + 未读 REVIEW 文件即可生成。

## 21. 测试集成

### SPEC 中的测试要求

每个 SPEC 的验收标准中至少包含一项测试相关条目：
- 功能测试："`paper-factory translate` 对 1 篇论文返回正确翻译"
- 边界测试："输入空字符串时返回错误提示而非崩溃"
- 如项目已有测试框架，SPEC 引用测试文件路径

### PHASE 中的测试执行

PHASE 的完成标准中包含：`- [ ] 测试通过`

测试不作为独立阶段——是每个 SPEC 施工的一部分。

## 22. 施工中改方向（In-Flight Reversal）

当已有施工代码的 SPEC 因 ADR 被推翻而需要改方向时：

1. **保留实验代码** — `git checkout -b experiment/SPEC-003-old-approach` 保存当前代码，然后切回原分支
2. **回退主分支** — `git revert` 或 `git reset` 撤消旧实现
3. **PHASE 标记** — 状态改为"废弃: ADR 推翻"，记录旧分支名供参考
4. **不删除旧代码** — 旧代码是有效的架构实验，保留在分支中可追溯
5. **新建 SPEC** — 基于新 ADR 创建新 SPEC，从头开始

## 23. 并行施工

多个 PHASE 可以同时"施工中"，前提是它们互不冲突：

### 并行条件

1. **无文件重叠** — 两个 SPEC 影响文件集合无交集（AI 通过 SPEC 的"关联模块"字段判断）
2. **无数据依赖** — SPEC A 的输入不依赖 SPEC B 的输出
3. **用户知情** — AI 告知"以下 SPEC 可以并行施工：..."

### 冲突检测

启动新 PHASE 前，AI 检查所有活跃 PHASE 的影响文件：
- 有重叠 → 建议串行或用户选择优先顺序
- 无重叠 → 允许并行

DESIGN-BOARD 中活跃 PHASE 超过 1 个时，顶部显示"🔀 并行施工中"。

## 24. ADR 依赖链

### ADR 模板新增字段

```markdown
- **依赖**: ADR-xxx, ADR-yyy（如有）
- **被依赖**: （AI 自动计算）
```

### 级联规则

当 ADR 被 superseded 时：
1. AI 扫描所有 ADR 的"依赖"字段 → 找到受影响的 ADR
2. 受影响 ADR 状态改为"待审查: 依赖 ADR-xxx 已废弃"
3. 在 DESIGN-BOARD 中标记关联
4. 用户逐个审查受影响 ADR → 更新或废弃

### 循环依赖检测

AI 在创建新 ADR 时检查：添加此依赖是否会形成循环？→ 循环依赖不允许，AI 拒绝创建并提示用户重新设计。

## 25. 非功能需求（NFR）

### CONSTITUTION 中记录

```markdown
## 非功能需求
| 类别 | 要求 | 指标 |
|------|------|------|
| 性能 | FTS5 搜索延迟 < 100ms | 待验证 |
| 安全 | 无外部网络访问 | 已满足 |
```

### SPEC 中引用

每个 SPEC 的验收标准中，将 NFR 转化为可测量条件：
- "搜索 10K 文档返回 < 100ms" → 引用 CONSTITUTION 的性能要求
- "不发起外部 HTTP 请求" → 引用 CONSTITUTION 的安全要求

## 27. 核心原则

1. **用户始终只是在聊天** — AI 负责判断阶段、创建文件、追踪关联
2. **结构优于智能** — 清晰的文档结构 > AI 的临场发挥
3. **冲突即对话** — 发现矛盾不静默处理，列出影响范围后问用户
4. **收敛是自动的** — AI 主动扫描，不要求用户记得触发
5. **适用于全新和既有** — 新项目从空白 DESIGN-BOARD，既有项目从代码倒推
6. **渐进式精度** — BRIEF 可以模糊，ADR 必须精确，SPEC 必须可执行
7. **追问有上限** — 每次最多 5 问，防止无限追问
8. **会话可持续** — 新会话自动恢复上下文，PHASE 状态追踪跨会话进度
9. **看板一句话** — 用户说"看板"就能看到全局状态，不用翻文件
10. **可移植** — 所有路径从 SKILL.md 自身位置推导，不在任何地方硬编码路径
11. **并行可控** — 独立 SPEC 可并行施工，AI 检测冲突
12. **链式追溯** — ADR 依赖链完整，改名/废弃时级联通知
13. **实验不丢** — 改方向时旧代码保留在 git 分支，不删除
